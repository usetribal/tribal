# Decision 0001 — Contract bindings: Rust types are the source of truth

**Status:** accepted (2026-06-12)

## Context

Lineage's data contracts (Conversation, LineObject, …) are consumed in two
languages: Rust (this repo — the local tooling) and TypeScript (the server
that ingests synced data). Until now the only cross-language artifact
was hand-written markdown in `specs/`, kept aligned with the `lineage-core`
serde types by review discipline alone. Drift between the two could only
surface at runtime, on the sync path — the worst possible place.

Four candidate architectures were evaluated against this rubric, in priority
order:

1. **Machine-checked single source of truth** — Rust/TS drift must fail CI,
   never surface at runtime.
2. **Evolution under asymmetric deployment** — the server updates instantly;
   CLI versions on user machines lag indefinitely. Additive evolution and
   old-client/new-server compatibility must be cheap and testable.
3. **Algorithm parity story** — how do `content_hash`, canonical
   serialization, patch-id, and redaction stay bit-for-bit identical across
   languages?
4. **Fidelity of generated code** — would we want to use the generated Rust
   and TS, or will people bypass it?
5. **Charter compliance** — truth must live in the open-source tree (public
   defines, closed consumes).
6. **DX** — contract change → both sides typecheck, in one short loop.

## Candidates

- **A. OpenAPI-first** (the server's ts-rest contract emits OpenAPI; Rust
  generates a client). Rejected: truth would live in the closed consumer —
  backwards per criterion 5 — and Rust OpenAPI codegen fidelity is middling
  (criterion 4). OpenAPI remains the *wire* description for the server's
  HTTP surface; it just doesn't define the shared types.
- **B. Neutral IDL: hand-written JSON Schema in `specs/`**, `typify` for
  Rust, zod codegen for TS. Direction-correct, but it adds a third
  hand-maintained artifact and generated Rust would replace `lineage-core`
  types that already exist and are good (criterion 4: every downstream crate
  would churn).
- **C. Protobuf-style IDL** (proto3/Smithy with JSON mapping). Best-in-class
  evolution semantics, but an awkward fit with both ends: the server stack
  is zod/ts-rest, the local stack is serde — both sides would be generated
  code nobody wants to read, plus a new toolchain dependency.
- **D. Rust-as-truth** (chosen): the existing `lineage-core` serde types are
  canonical. `schemars` derives JSON Schema from them; the committed
  `specs/schema/*.schema.json` artifacts are snapshot-tested against the
  types; TypeScript zod bindings (`contracts/ts`, `@lineage/contracts`) are
  generated from those schemas and drift-checked the same way.

## Decision

**D — Rust-as-truth, with golden conformance vectors for algorithm parity.**

The pipeline, each hop machine-checked:

```text
lineage-core types  --schemars-->  specs/schema/*.schema.json  --json-schema-to-zod-->  contracts/ts
        |                                   |                                                |
  cargo test (snapshot test          committed artifact                       committed artifact, checked by
  fails on drift, regenerates        (reviewable diff on                      `check:drift` before every build
  with LINEAGE_UPDATE_SCHEMAS=1)     every contract change)                   (regenerate with `generate`)
```

- `specs/schema/` is the canonical *artifact* consumers read; `lineage-core`
  is the canonical *definition* it is generated from. The prose specs in
  `specs/*.md` stay as narrative documentation; their normative tables
  progressively defer to the generated schemas.
- The spike validated the full pipeline on `LineObject`: enum renames, the
  transparent `LineageId` newtype, the `[u32; 2]` tuple, and optional fields
  all survive both hops with full fidelity, and a Rust-emitted document
  validates under the generated zod schema. Both drift checks were proven to
  fail on deliberate drift.
- **Evolution discipline is convention, borrowed from proto3:** new fields
  are optional-with-default (`#[serde(default)]`), enums grow but never
  rename values, nothing is removed or repurposed within a major schema
  version. Old-client/new-server compatibility is tested with conformance
  vectors, not left to review.
- **Algorithm parity is out of schema's reach by construction.** Types
  travel via schemas; algorithms (`content_hash`, canonical serialization,
  patch-id, redaction) do not. Golden conformance vectors in
  `specs/conformance/` — input document → expected hash/serialization output,
  generated by the Rust reference implementation — are executed by both the
  Rust and TS test suites in CI. If hashing parity proves fragile in
  practice, the escalation path is compiling `lineage-core`'s
  hashing/canonicalization to WASM and calling the single implementation
  from TS.

## Known limitations (accepted)

- `json-schema-to-zod` does not resolve `$ref`; the generator inlines
  internal `$defs` before conversion, so shared sub-schemas are duplicated
  inline in the TS output rather than exported as named schemas. Acceptable
  while bindings are machine-consumed; revisit if humans start importing
  sub-schemas directly.
- The TS side is two generation hops from the truth. The drift checks at
  each hop are what make this safe; do not hand-edit anything under
  `contracts/ts/src/generated/` or `specs/schema/`.
- Validation expressed in Rust code (e.g. `validate()` methods) rather than
  in the type structure does not reach the schemas. Anything the wire
  protocol must enforce belongs in the type structure or in the sync
  protocol spec, not in out-of-band Rust logic.
